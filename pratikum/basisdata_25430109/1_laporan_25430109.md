### 2. Ringkasan Dasar Teori
Basis data relasional dipakai untuk menyimpan data toko online, seperti pelanggan, produk, pesanan, dan transaksi, dalam tabel-tabel yang saling terhubung.
Untuk mengatur strukturnya, kita menggunakan perintah **DDL (Data Definition Language)**:
* **`CREATE`**: Membuat database atau tabel baru.
* **`ALTER`**: Mengubah struktur tabel.
* **`DROP` / `TRUNCATE`**: Menghapus tabel atau isinya.
Agar data efisien dan tidak duplikat, perhatikan dua hal penting berikut:
* **Tipe Data**: Contohnya `INT` untuk stok. `DECIMAL` untuk harga. `VARCHAR` untuk teks seperti alamat atau nama produk.
* **Constraint**: Gunakan `PRIMARY KEY` sebagai identitas unik untuk setiap baris. Pakai `FOREIGN KEY` untuk menghubungkan relasi antar tabel.

### 4. Jawaban Titik Analisis
* **Titik Analisis 1: MySQL vs. MariaDB**
* **Mencari Solusi di Internet:** Walaupun MariaDB adalah pecahan (*fork*) dari MySQL, sekarang keduanya sudah berkembang sendiri dengan sistem internal yang berbeda. Ketika mencari solusi dengan kata kunci "MySQL", kadang ada sintaks, fitur, atau letak berkas konfigurasi (`my.ini` vs `my.cnf`) yang tidak sama persis di MariaDB.
* **Kapan Dokumentasi MySQL Relevan:** Masih sangat berguna untuk sintaks dasar SQL yang umum. Contohnya adalah perintah `SELECT`, `INSERT`, `UPDATE`, `DELETE`, pembuatan tabel, atau relasi dasar.
* **Kapan Harus ke Dokumentasi MariaDB:** Harus dicek saat memakai fitur khusus MariaDB. Contohnya, *storage engine* seperti *Aria*, pengaturan *Galera Cluster*, atau fungsi *sequence* bawaan.
* **Titik Analisis 2: Akses Tanpa Sandi (`mysql -u root`)**
* **Pesan Galat yang Muncul:**
`ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: NO)`
* **Bagian yang Menandakan Tanpa Password:** Lihat teks `(using password: NO)` di bagian akhir. Ini menunjukkan percobaan masuk ke server tanpa opsi kata sandi, misalnya kurang argumen `-p`.
* **Perbandingan:** Jika memasukkan kata sandi namun salah, keterangannya akan langsung berubah menjadi `(using password: YES)`.
* **Titik Analisis 3: Hak Akses `information_schema` vs `mysql` (ERROR 1044 vs 1045)**
* **Penyebab `information_schema` Bisa Dibuka sedangkan `mysql` Ditolak:**
`information_schema` adalah direktori *read-only* yang berisi struktur metadata database, seperti nama tabel dan kolom. Database ini wajib dapat diakses oleh siapa saja yang berhasil login. Dengan begitu, aplikasi atau tools klien bisa membaca struktur sistem. Sebaliknya, database `mysql` menyimpan data sensitif tentang akun pengguna, kata sandi, dan hak akses (*privileges*). Karena itu, akses ke database tersebut ditolak untuk akun biasa demi keamanan.
* **Perbedaan ERROR 1044 dan 1045:**
* **ERROR 1044:** Terjadi setelah berhasil login. Namun, error ini muncul saat mencoba mengakses atau mengubah database yang tidak punya hak akses.
* **ERROR 1045:** Terjadi pada tahap awal login karena salah memasukkan *username*, kata sandi, atau *host* yang tidak diizinkan.
* **Titik Analisis 4: Keamanan phpMyAdmin (Mode `cookie` vs `config`)**
* **Kekurangan Mode `config`:** Kata sandi dan *username* ditulis langsung tanpa perlindungan di dalam berkas konfigurasi server (`config.inc.php`). Jika server bocor, kata sandi database bisa langsung terlihat. Siapa saja yang membuka tautan phpMyAdmin bisa langsung masuk tanpa otentikasi.
* **Kelebihan Mode `cookie`:** Kata sandi tidak disimpan secara permanen di berkas server. Pengguna harus memasukkan *username* dan kata sandi setiap kali masuk. Sesi login terenkripsi di dalam *cookie* peramban dan akan otomatis terhapus saat *logout* atau ketika menutup peramban. Hal ini membuatnya jauh lebih aman.

* **Kode Program / Cuplikan Hasil Modifikasi:**
```sql
CREATE TABLE IF NOT EXISTS pengguna (
id_pengguna INT(2) NOT NULL AUTO_INCREMENT,
nama_lengkap VARCHAR(25) NOT NULL,
email VARCHAR(30) NOT NULL,
kata_sandi VARCHAR(255) NOT NULL,
no_telepon VARCHAR(12) DEFAULT NULL,
alamat TEXT DEFAULT NULL,
peran ENUM('pelanggan', 'admin') NOT NULL DEFAULT 'pelanggan',
tanggal_daftar DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
PRIMARY KEY (id_pengguna),
UNIQUE KEY email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS kategori (
id_kategori INT(2) NOT NULL AUTO_INCREMENT,
nama_kategori VARCHAR(50) NOT NULL,
slug VARCHAR(50) NOT NULL,
id_induk INT(2) DEFAULT NULL,
PRIMARY KEY (id_kategori),
UNIQUE KEY slug (slug),
KEY fk_kategori_induk (id_induk),
CONSTRAINT fk_kategori_induk FOREIGN KEY (id_induk)
REFERENCES kategori (id_kategori) ON DELETE SET NULL ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS produk (
id_produk INT(2) NOT NULL AUTO_INCREMENT,
sku VARCHAR(30) DEFAULT NULL,
nama_produk VARCHAR(50) NOT NULL,
deskripsi TEXT DEFAULT NULL,
harga DECIMAL(10,2) NOT NULL DEFAULT 0.00,
stok INT(3) NOT NULL DEFAULT 0,
berat_gram INT(2) NOT NULL DEFAULT 0,
id_kategori INT(2) DEFAULT NULL,
gambar VARCHAR(30) DEFAULT 'default.jpg',
status ENUM('aktif', 'nonaktif') NOT NULL DEFAULT 'aktif',
dibuat_pada DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
PRIMARY KEY (id_produk),
UNIQUE KEY sku (sku),
KEY fk_produk_kategori (id_kategori),
CONSTRAINT fk_produk_kategori FOREIGN KEY (id_kategori)
REFERENCES kategori (id_kategori) ON DELETE SET NULL ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS pesanan (
id_pesanan INT(2) NOT NULL AUTO_INCREMENT,
nomor_pesanan VARCHAR(30) NOT NULL,
id_pengguna INT(2) NOT NULL,
tanggal_pesan DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
total_harga DECIMAL(10,2) NOT NULL DEFAULT 0.00,
ongkos_kirim DECIMAL(8,2) NOT NULL DEFAULT 0.00,
alamat_pengiriman TEXT NOT NULL,
status_pesanan ENUM('menunggu_pembayaran', 'diproses', 'dikirim', 'selesai', 'dibatalkan') NOT NULL DEFAULT 'menunggu_pembayaran',
PRIMARY KEY (id_pesanan),
UNIQUE KEY nomor_pesanan (nomor_pesanan),
KEY fk_pesanan_pengguna (id_pengguna),
CONSTRAINT fk_pesanan_pengguna FOREIGN KEY (id_pengguna)
REFERENCES pengguna (id_pengguna) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS detail_pesanan (
id_detail INT(2) NOT NULL AUTO_INCREMENT,
id_pesanan INT(2) NOT NULL,
id_produk INT(2) NOT NULL,
jumlah INT(3) NOT NULL DEFAULT 1,
harga_satuan DECIMAL(10,2) NOT NULL DEFAULT 0.00,
subtotal DECIMAL(12,2) NOT NULL DEFAULT 0.00,
PRIMARY KEY (id_detail),
KEY fk_detail_pesanan (id_pesanan),
KEY fk_detail_produk (id_produk),
CONSTRAINT fk_detail_pesanan FOREIGN KEY (id_pesanan)
REFERENCES pesanan (id_pesanan) ON DELETE CASCADE ON UPDATE CASCADE,
CONSTRAINT fk_detail_produk FOREIGN KEY (id_produk)
REFERENCES produk (id_produk) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE IF NOT EXISTS pembayaran (
id_pembayaran INT(2) NOT NULL AUTO_INCREMENT,
id_pesanan INT(2) NOT NULL,
metode_pembayaran VARCHAR(50) NOT NULL,
bukti_pembayaran VARCHAR(100) DEFAULT NULL,
jumlah_bayar DECIMAL(12,2) NOT NULL DEFAULT 0.00,
tanggal_bayar DATETIME DEFAULT NULL,
status_pembayaran ENUM('menunggu', 'diverifikasi', 'gagal') NOT NULL DEFAULT 'menunggu',
PRIMARY KEY (id_pembayaran),
KEY fk_pembayaran_pesanan (id_pesanan),
CONSTRAINT fk_pembayaran_pesanan FOREIGN KEY (id_pesanan)
REFERENCES pesanan (id_pesanan) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 7. Pembahasan dan Kendala
* **Pembahasan:** Pada praktikum ini, perintah DDL (CREATE, ALTER) berhasil membentuk struktur basis data toko online dan lingkungan proyek e-commerce. Penentuan tipe data seperti INT untuk ID atau stok, VARCHAR untuk teks dinamis, dan DECIMAL untuk harga produk sudah sesuai dengan aturan perancangan basis data relasional. Penerapan integrity constraint seperti PRIMARY KEY dan FOREIGN KEY menjaga konsistensi relasi antara tabel kategori dan tabel produk. Hal ini mencegah data produk tanpa kategori induk yang valid. Pada konfigurasi pengguna, penerapannya sudah sesuai dengan prinsip keamanan least privilege. Akun dev_109 hanya mendapat hak akses pada database tokodaring_109 untuk mencegah pengaksesan atau modifikasi tidak sah pada database lain.

* **Kendala dan Solusi:**
* Kendala 1: Saat menambah Foreign Key pada tabel produk, muncul eror karena tipe data kolom id_kategori di tabel induk (kategori) dan tabel anak (produk) tidak persis sama.
Solusi: Pastikan tipe data kedua kolom sama, yaitu INT NOT NULL.
* Kendala 2: Login dengan akun dev_109 di terminal sempat ditolak (ERROR 1045) setelah pendaftaran akun baru.
Solusi: Jalankan perintah FLUSH PRIVILEGES; lebih dulu dengan akun administrator (root). Ini akan memperbarui tabel hak akses sistem MariaDB.
