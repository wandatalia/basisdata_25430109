## 1. Tujuan Praktikum

Pada pertemuan pertama ini, praktikum bertujuan untuk memberikan pemahaman awal mengenai lingkungan kerja Database Management System (DBMS) serta pengoperasian tools pendukungnya. Melalui praktikum ini, praktikan diharapkan mulai terbiasa menggunakan kueri-kueri dasar SQL yang nantinya akan menjadi fondasi utama dalam mengelola sistem basis data secara keseluruhan, mulai dari proses pembuatan database hingga pengelolaan tabel.

Selain pengenalan tools, praktikum ini juga bertujuan untuk melatih keterampilan dalam merancang dan membuat struktur basis data awal yang difokuskan pada studi kasus toko online. Praktikan diajarkan cara mengeksekusi perintah Data Definition Language (DDL) seperti `CREATE`, `ALTER`, dan `DROP` untuk membangun tabel-tabel utama yang dibutuhkan, seperti tabel pengguna, kategori, katalog produk, hingga entitas transaksi pesanan.

Melalui skenario toko online tersebut, praktikan dituntut untuk mampu menganalisis penggunaan tipe data yang presisi serta penentuan aturan batas (*constraint*) seperti `PRIMARY KEY`, `FOREIGN KEY`, dan `NOT NULL` pada tiap kolom. Hal ini bertujuan agar data transaksi, stok barang, maupun profil pelanggan yang tersimpan dalam sistem nantinya dapat terstruktur dengan rapi, terhubung secara valid, dan terhindar dari potensi redundansi atau kesalahan input data.

## 2. Ringkasan Dasar Teori

Basis data relasional merupakan sekumpulan data terstruktur yang disimpan dalam bentuk tabel-tabel terpisah namun saling berhubungan satu sama lain melalui suatu kunci penghubung. Dalam pengembangan aplikasi toko online, penerapan basis data relasional sangat krusial untuk memastikan seluruh entitas—seperti data akun pelanggan, daftar katalog produk, riwayat pemesanan, hingga detail transaksi pembayaran—dapat terorganisir dengan konsisten dan mudah diakses kembali melalui kueri SQL.

Untuk mengelola dan memanipulasi struktur basis data tersebut, digunakan kelompok perintah SQL yang dikenal sebagai Data Definition Language (DDL). Perintah DDL ini meliputi kueri `CREATE` untuk membuat database atau tabel baru, `ALTER` untuk memodifikasi struktur kolom yang sudah ada, serta `DROP` atau `TRUNCATE` untuk menghapus objek basis data. Penguasaan kueri DDL menjadi fondasi utama dalam merancang skema toko online agar mampu menampung atribut penting seperti nama produk, harga, stok, dan kode identifikasi barang.

Selain skema dan kueri, faktor penentu keberhasilan perancangan basis data terletak pada pemilihan tipe data serta penerapan aturan pembatas (*constraint*). Penggunaan tipe data yang tepat, seperti `INT` untuk kuantitas stok, `DECIMAL` untuk nominal harga, serta `VARCHAR` untuk teks dinamis seperti alamat atau SKU produk, sangat penting untuk efisiensi penyimpanan. Dipadukan dengan *constraint* seperti `PRIMARY KEY` sebagai identitas unik baris data dan `FOREIGN KEY` sebagai penyambung relasi antartabel, basis data toko online yang dibangun akan terjamin integritas datanya dan terhindar dari duplikasi data yang tidak diinginkan.

## Jawaban Titik Analisis
### Titik Analisis 1: MySQL vs. MariaDB

* **Konsekuensi saat mencari solusi galat di internet:**
  * MariaDB adalah *fork* dari MySQL, tetapi kedua DBMS ini telah berkembang secara terpisah dengan fitur, fungsi internal, dan mesin penyimpanan yang berbeda.
  * Jika mencari solusi menggunakan kata kunci "MySQL", beberapa sintaks atau fitur canggih mungkin tidak berfungsi pada MariaDB (atau sebaliknya). Selain itu, nomor galat (*error code*) atau lokasi berkas konfigurasi (`my.cnf` vs `my.ini`) bisa berbeda.
* **Kapan dokumentasi MySQL masih relevan:**
  * Dokumentasi MySQL masih sangat relevan untuk **sintaks SQL dasar** (seperti `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE TABLE`), pembuatan indeks standar, perintah *join* sederhana, dan perintah dasar DDL/DML.
* **Kapan harus merujuk ke dokumentasi MariaDB:**
  * Harus merujuk ke dokumentasi MariaDB ketika menghadapi **fitur/mesin penyimpanan spesifik MariaDB** (seperti *Aria*, *ColumnStore*, *Galera Cluster*), pengaturan otentikasi hak akses khusus, pembuatan *sequence*, sintaks JSON/PL/SQL bawaan MariaDB, serta konfigurasi variabel server versi terbaru.

  ### Titik Analisis 3: Hak Akses `information_schema` vs `mysql` (ERROR 1044 vs 1045)

* **Alasan `information_schema` Tetap Terlihat, Sedangkan `mysql` Ditolak dengan ERROR 1044:**
  * **`information_schema`** adalah skema sistem bawaan berbasis pandangan baca-saja (*read-only views*) yang memuat metadata tentang struktur seluruh basis data (seperti nama tabel, kolom, tipe data, dan hak akses)[cite: 35, 43]. Setiap pengguna yang berhasil terautentikasi **wajib** memiliki akses ke skema ini agar perkakas klien (seperti CLI MariaDB atau phpMyAdmin) dapat mengenali objek apa saja yang diizinkan untuk dikelola oleh akun tersebut[cite: 35].
  * **`mysql`** adalah basis data internal utama (*system database*) yang menyimpan data fisik autentikasi server, daftar akun pengguna, kredensial, serta pemetaan hak akses (*privileges*)[cite: 34, 35]. Karena akun `mhs_123` adalah akun kerja biasa dan bukan *superuser/root*, server menolak akses ke basis data `mysql` demi menjaga keamanan agar pengguna biasa tidak dapat melihat atau mengubah data sensitif pengguna lain[cite: 34, 35].
* **Perbedaan Kode Galat 1044 dan 1045:**
  * **ERROR 1044 (42000) - *Access denied for user to database*:** Terjadi **setelah pengguna berhasil masuk/login** ke server[cite: 35], tetapi pengguna tersebut mencoba mengakses atau melakukan operasi pada suatu basis data di mana ia **tidak memiliki hak akses (*privileges*)**[cite: 35, 119].
  * **ERROR 1045 (28000) - *Access denied for user (using password: ...)*:** Terjadi **pada saat proses otentikasi/login awal**[cite: 39, 119], akibat nama pengguna (*username*), kata sandi (*password*), atau *host* asal koneksi tidak cocok/salah[cite: 39, 119].

  ### Titik Analisis 4: Keamanan Mode Cookie vs Mode Config pada phpMyAdmin

* **Mengapa Mode `cookie` Lebih Aman daripada Mode `config`:**
  1. **Penyimpanan Kata Sandi Teks Polos (*Plaintext*):**
     Pada mode `config`, kata sandi disimpan langsung secara teks polos (*plaintext*) di dalam berkas konfigurasi `config.inc.php` pada server web[cite: 37, 39]. Jika server mengalami celah keamanan (seperti *Directory Traversal* atau kesalahan izin akses berkas), pihak yang tidak berhak dapat membaca berkas tersebut dan memperoleh kata sandi secara langsung[cite: 39].
  2. **Akses Terbuka Tanpa Otentikasi Ulang:**
     Pada mode `config`, siapa pun yang mengakses URL phpMyAdmin di peramban web akan langsung masuk (*login*) secara otomatis tanpa memvalidasi identitas atau memasukkan kata sandi kembali[cite: 35, 37].
  3. **Mekanisme Keamanan Mode `cookie`:**
     Pada mode `cookie`, kata sandi tidak pernah disimpan secara permanen di dalam berkas server web[cite: 37]. Pengguna diwajibkan mengetikkan nama pengguna dan kata sandi setiap kali memulai sesi[cite: 37]. Kredensial ini disimpan sementara dalam bentuk *cookie* peramban yang terenkripsi dan otomatis hancur (*expire*) saat sesi diakhiri atau saat pengguna melakukan *logout*[cite: 37].
